# AI 音樂專案（鼓譜轉譜／AI 音樂編輯器）聊天整理

> 狀態標記：**明確決策**＝使用者明確選定／**討論提案**＝提過但沒定案／**待確認**＝傾向或前提存在但未拍板，或屬調研資訊需自行驗證。
> 方括號 [C#] 對應文末「參考聊天」編號。

## Product Vision

- **明確決策**　產品是給鼓手用的網頁工具：上傳音訊 → 自動轉成鼓譜 → 在內建編輯器手動修正。[C2]
- **明確決策**　目標是商業化。[C2]
- **明確決策**　希望用使用者修正後的資料，回頭改善辨識能力。[C2]
- **明確決策**　要讓使用者能用說話（與 AI 對話）的方式修改鼓譜。[C4][C5]
- **待確認**　差異化方向：以轉譜 API（如 Klangio）當引擎，把編輯體驗（聽著選、批次修正、不確定標示）與修正回饋做成賣點。使用者回應「聽起來蠻合理」，未正式定案。[C2]
- **討論提案**　市場定位：「上傳你的錄音，把練習轉成譜」（鼓手練習、老師出教材、樂團記錄自己的編曲）比「一鍵取得任何歌曲的鼓譜」在版權上安全，且客群付費意願不低。[C2]
- **討論提案**　作品集價值：語音編輯（應用架構）＋資料飛輪（評估）＋Klangio 整合與上線（系統設計）可串成一個完整的 AI 工程作品。[C7]
- **待確認**　競品調研（需自行驗證）：Klangio Drum2Notes（有 API、線上編輯器、匯出 MusicXML／MIDI／PDF；App Store 評分約 3.8，有使用者抱怨結果與原曲無關）；Paradiddle（三模型投票、公開 F1 0.86、標示不確定擊點讓使用者確認並作為訓練資料；未見對外 API；使用者當時找不到該網站）；DrumScript（開源規則式）；AnthemScore（編輯功能弱）；Drumscrib、DrumConvert、NotaGen。[C2]
- **待確認**　宣傳影片已製作（30 秒、1080p），使用暫定名「打譜」與 slogan「上傳 轉譜 開打」；影片把語音編輯呈現為現有功能。[C9]

## UX / User Flow

- **明確決策**　主流程：上傳音訊（可整首歌）→ 自動轉譜 → 進入內建編輯器修正。[C2]
- **明確決策**　模型不確定的決策點，提供 2–3 個候選方案，每個附一小段譜（約 2–4 小節）＋對應音訊，讓使用者聽著選。使用者表示「這就是我理想的狀況」。[C2]
- **明確決策**　編輯器以五線譜呈現（使用者表示預期是五線譜）。[C2]
- **討論提案**　需人確認的點與順序：拍號與小節起點 → tempo 倍數（半速／倍速）→ 網格解析度（十六分 vs 三連音）→ 鼓類別（tom／snare、ride／hi-hat）→ 重音。前面錯會傳遞到後面。[C2]
- **討論提案**　候選片段挑鼓最密最穩的段落（通常是副歌），不用前奏；播放時加小節開頭提示音或畫面閃爍。[C2]
- **討論提案**　拍號預設 4/4；可手動改拍號、在特定小節插入變拍、拖動小節線或「以這一擊為第一拍」。[C2]
- **討論提案**　編輯器互動：播放同步游標、單小節循環、鍵盤操作（數字鍵對應鼓種、方向鍵移動、空白鍵播放）、批次編輯（複製到相似小節、全部把某位置的 tom 改成 snare）、低信心擊點用顏色標示。[C2]
- **討論提案**　等待體驗：依 pipeline 階段回報進度、每處理約 30 秒就先出那段譜可先編輯、先用能量法給粗略擊點預覽、做成任務列表＋完成通知。[C2]
- **討論提案**　渲染元件：VexFlow（吃自有資料畫譜，編輯互動要自己做）、OpenSheetMusicDisplay（吃 MusicXML、較美觀但編輯要自理）、Flat.io（可嵌入但付費）；另有 Songsterr 式格線／tab 介面可選。[C2]
- **討論提案**　使用者提出：使用前先讓使用者把每個鼓各打幾下錄成音色模板。Claude 建議只當信心低時的輔助校正（MFCC／梅爾頻譜比對），且只適用單獨錄鼓、不適用混音。[C2]

## MVP Scope

- **討論提案**　先不做 Demucs，直接跑轉譜模型看準確度，特定樂風不夠準再加成開關。[C2]
- **討論提案**　先跑原始模型、不先微調；先累積資料觀察錯誤模式。[C2]
- **討論提案**　力道只分 2–3 級（重音／普通），不做連續數值。[C2]
- **討論提案**　快速 MVP 可用 Klangio API。[C8]
- **討論提案**　Claude 排的 16 週時程（與課程綁定）：W1 串 Klangio API、W2 定義鼓譜操作工具 schema、W3 準備 100 句口語指令測試集、W4 量測指令解析準確率、W5 接 STT 完成「說話 → 指令 → 改譜」，第二階段（10/26–11/22）做出語音編輯 MVP。[C7]

## Internal Music Model

- **討論提案**　三層資料模型：(1) 原始偵測（時間點、鼓類別、信心分數；永不修改）(2) 量化後的譜（第幾小節第幾拍、音符長度；可重算）(3) 使用者編輯操作紀錄（刪除擊點、tom 改 snare、新增擊點等；不覆蓋中間層）。[C2]
- **討論提案**　模型輸出先存成中性中間格式（時間＋類別＋信心），量化邏輯改了可以重跑，不必重新推論。[C2]
- **討論提案**　編輯器內部用自訂 JSON 結構，不直接操作 MusicXML 或 MIDI；匯出時才轉換。[C2]
- **討論提案**　匯出 MIDI＋MusicXML 兩種（開放標準、函式庫現成）；Guitar Pro 格式對鼓手實用；ABC notation 不適合鼓譜；MuseScore 格式封閉。[C2]

## Audio → Transcription → Score

- **明確決策**　離線辨識即可，不做即時串流。[C2]
- **討論提案**　Pipeline：ffmpeg 統一格式（單聲道、固定取樣率）→（可選）Demucs 分離鼓軌 → 轉譜模型抓擊點與鼓類別 → tempo 估計／beat tracking → 動態選網格量化 → 切分小節 → 計算音符長度 → 渲染鼓譜 → 使用者修正回饋。已產出 ELI5 單頁 HTML 圖解。[C1][C2]
- **待確認**　ADTOF：開源主流基準、5 類鼓（大鼓、小鼓、hi-hat、tom、銅鈸）、CRNN、多標籤可處理同時擊打；但程式碼為 CC BY-NC-SA 4.0、資料集限非商業，無法直接商用。可行路線：寫信向作者 Matthias Zehren 談商業授權／依論文自行訓練／改接商用 API。[C2]
- **待確認**　轉譜引擎改用 Klangio API：使用者以「如果外接 Klangio API」為前提提問，之後的規劃都以此為前提，但對話中未見明確拍板。[C2][C7]
- **待確認**　其他鼓轉譜選項調研（需自行驗證）：DrumScript（規則式、輸出 PDF／MIDI／MusicXML，授權待查）、DrummerScore（MIT，但只是學士論文 notebook、未經標準評測）、ADTLib（3 類、較舊）、ADTOF-pytorch（授權問題可能相同）、Enhanced ADT via Drum Stem Source Separation（8 類＋力道，研究授權）、Noise-to-Notes、STAR Drums；Moises、Music AI 鼓譜表現不明；Basic Pitch 不適合鼓。[C2]
- **待確認**　通用轉譜服務比較（需自行驗證）：Klangio API（REST，MIDI／MusicXML／PDF／GP5，單檔 300 秒限制需先切段）、Mirelo Audio-to-MIDI Pro API（官方 Node.js／TypeScript SDK、多樂器）、Transkun（鋼琴、MIT、可 ONNX）、Spotify Basic Pitch（Apache-2.0、npm 套件、只出 MIDI）、MuScriptor（權重 CC BY-NC 4.0 不可商用）。[C8]
- **討論提案**　Demucs（htdemucs）定位是「分離」、ADTOF 是「辨識」，前後串接。Demucs 吃資源（CPU 跑一首可能數分鐘）、會留 artifact；編曲厚重（如金屬）時有利，乾淨編曲（如爵士三重奏）反而有損。[C2]
- **討論提案**　是否跑 Demucs 的判斷：用音訊統計特徵規則分流，或「兩路都跑、比較信心分數」事後選擇，甚至融合兩路結果。[C2]
- **討論提案**　量化：假設十六分／三連音／三十二分等網格，以小節或半小節為單位選誤差最小者，越細的網格加懲罰項；真人打鼓 tempo 會漂，需 beat tracking。[C2]
- **討論提案**　打不準的校正：低信心擊點放寬吸附；用小節間重複的 pattern 互相校正；階層式（先定大鼓／小鼓骨架，再對 hi-hat）；不確定時回看音訊能量曲線找峰值。[C2]
- **討論提案**　力道（velocity）：ADTOF 不提供，從擊點附近短時能量估計、分頻段處理重疊、局部視窗正規化；或改用 E-GMD 訓練的 Onsets and Frames Drums 取得較準的力道。[C2]
- **討論提案**　拍號：可用重音週期推估，但變拍（如 progressive metal）自動判斷不可靠，交給人確認。[C2]
- **討論提案**　若引擎只輸出 MIDI，需後處理：量化、拍號推斷、聲部分離，再用 MuseScore CLI 或 Verovio 渲染。[C8]
- **討論提案**　準確度評估：precision／recall／F，±50ms 容錯窗，分鼓種看（hi-hat 通常較低）；標準答案可用使用者修正後的資料。[C2]

## AI Agent Architecture

- **討論提案**　三段式流程（使用者自己描述、Claude 確認）：語音轉文字 → Jev 判斷意圖（新增／刪除／修改音符、調速度等）→ 分類結果＋原句交給 LLM 抽參數（小節、拍、音符類型）並產生結構化指令或腳本 → 自己的程式執行改譜。[C4][C6]
- **待確認**　Jev（TypeSafe AI，early access）只輸出固定形式（選項、分數、是非），不能抽取任意數值，也不能輸出 MusicXML 這類自由格式；官方宣稱比前沿模型快 40–200 倍、便宜 40–400 倍，接入前需自測。[C4]
- **討論提案**　Jev 的價值在成本、延遲，以及不會冒出未定義的動作；若指令種類不多，一開始只用 LLM＋嚴格 schema 也夠。[C6]
- **討論提案**　信心門檻：看最高分的絕對值與第 1、2 名差距。分數高但差距小 → 反問二選一；分數普遍偏低 → 告知聽不懂（範圍外）。後端回「需要澄清」狀態並帶前兩個候選意圖，前端轉成問句；使用者選完後連同原句送回，跳過分類直接執行。[C6]
- **討論提案**　類 Cursor 設計：模型不重寫整份譜，只輸出符合 schema 的小編輯（action、target range、parameters），允許動作如 replace pattern、change tempo、add fill、delete bars；實際編輯由自己的程式執行，模型不直接碰譜。[C5]
- **討論提案**　兩段式取上下文：第一輪只給選取的小節＋整首結構大綱（主歌／副歌在哪幾小節）；資訊不足時，模型回傳「要資料」動作（與編輯動作放在同一個 schema），程式補入指定小節再跑第二輪。[C5]
- **討論提案**　套用前先驗證（小節是否存在、pattern 是否支援），不符就拒絕。[C5]
- **討論提案**　在 NestJS 裡把 Jev 當成一個 service 呼叫。[C4]
- **討論提案**　語音編輯本質是「一句話 → 一個或幾個工具呼叫」，用不到長時間、多步驟的重型 agent 架構。[C7]
- **討論提案**　（選做）把鼓譜編輯功能包成 MCP server。[C7]

## Text / Voice Editing

- **明確決策**　要做語音編輯：使用者說話 → 轉文字 → 指令 → 修改鼓譜。[C4][C5]
- **討論提案**　考慮整合 TypeSafe AI（Jev）作為分類／結構化層。[C4][C5]
- **討論提案**　STT 用本地 Whisper（不按音訊秒數付費）或 GCP 語音轉文字，只把轉出的短句送模型。[C4][C5]
- **討論提案**　錄音時同時擷取目前選取的小節、tempo 等當上下文。[C5]
- **待確認**　指令目標範圍：有選取時以選取範圍為準（使用者提出、Claude 同意）；無選取但話裡明講（「第十二小節」「最後四小節」）就照講的做。[C6]
- **討論提案**　工具 schema 操作：加音、刪音、改樂器、改力度，例如 `add_hit(measure=3, beat=2, instrument="snare")`。[C7]
- **討論提案**　準備 100～數百句口語指令當測試集，例如「把第十小節第四拍補上一個四連音」「第三小節的小鼓改輕一點」「把那個 fill 刪掉」「make bar twelve a half-time shuffle」。[C4][C5][C7]

## Diff / Versioning

- **明確決策**　AI 改動以「拍（beat）」為單位呈現「修改前／修改後」，不逐音符標示新增或刪除，避免六連音等密集段落雜亂。[C10]
- **討論提案**　beat 級 mockup：主譜顯示「修改後」，只有被改的拍上方多一列淡化的「修改前」；淡灰藍背景框住同一拍的兩版本、中間虛線分隔；密集拍自動變寬並按時間對齊。[C10]
- **待確認**　使用者以「同一個 commit（提交）」描述一批 AI 改動，表示改動以 commit 為單位，但 commit 的定義與資料結構未討論。[C10]
- **討論提案**　每個被改的拍提供「接受／還原這一拍」，讓審閱單位與呈現單位一致（Claude 建議）。[C10]
- **討論提案**　（已被 beat 級取代的音符級版本）綠色＝新增、半透明紅＝刪除，拍背景改中性色並標 `+2`／`+1 −1`；同位置同樂器「刪了又加回」（只改力度、重音、ghost note）應合併成「修改」狀態。[C10]
- **討論提案**　使用者的修正以一筆筆「編輯操作」儲存（三層模型最上層），可復原，也可比對模型錯在哪。[C2]
- **討論提案**　語音編輯以可復原操作套用並高亮，使用者可說「不對，復原」。[C5]

## Local-first / GitHub Architecture

- **討論提案**　音訊處理三種做法：(a) 純本地：ADTOF 轉 ONNX、用 onnxruntime-web 在瀏覽器跑（模型小可行，但 Demucs 跑不動）(b) 暫時上傳、處理完即刪，只留譜 (c) 音訊只存在瀏覽器 IndexedDB。Claude 建議 (b)。[C2]
- **待確認**　使用者選擇深入 (b)，並複述設計：雲端只存音檔 hash 並與譜綁定；使用者下次在本地選同一個檔案，以 hash 配對後用 File API 在本地播放，不必再上傳音檔。未明確宣告定案。[C2]
- **討論提案**　hash 細節：整檔 SHA-256 要用 Web Worker，或只算前幾 MB＋檔案大小；使用者轉檔（MP3 ↔ WAV）導致 hash 不符時只警告、不阻擋；對外要講清楚是「只上傳一次」而非完全不上傳。[C2]
- **討論提案**　使用者提出：讓使用者把音訊放在自己的雲端空間（如 Google Drive、Dropbox），服務只在處理時暫時讀取。[C2]
- **討論提案**　CI/CD：GitHub Actions 同時做 CI 與 CD 步驟，搭配 Vercel 或 Render 由 GitHub push 自動部署。[C3]

## Free vs Paid

- **討論提案**　使用者提出分方案：基本版走單一路徑；進階版有／無 Demucs 兩路都跑再比對。Claude 建議基本版給免費使用者、進階版（雙路融合）當付費功能，且兩路結果不一致處可在編輯器標示「請確認」。[C2]
- **待確認**　競品定價（需自行驗證）：Paradiddle 第一首免費、之後付費（價格未查到）；Drumscrib 每首約 US$1.8–3.6；DrumConvert 訂閱每月約 US$9–29。[C2]
- **待確認**　成本面（需自行驗證）：Klangio API 分級約 $0–$499+／月，成本隨用量增加；Mirelo 約每分鐘 €0.11–0.14。[C2][C8]
- **討論提案**　商業化的版權防護：上傳前勾選框聲明有權處理檔案（必要但不充分）；轉錄他人歌曲的鼓譜在多數法域可能屬衍生作品，收費前建議諮詢律師；Klangio 服務條款可能限制用其輸出訓練競爭模型。[C2][C7]
